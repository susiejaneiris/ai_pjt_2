## 3. RAG 파이프라인 설계 (명세 2.3~2.6 · 제출물 2)

### 3-1. 전체 흐름
```
⓪ 실행 전 (RAG 1) ── python -m scripts.build_index
   items.json(276) ─► 항목 텍스트 구성 ─► 임베딩 ─► [law_meta]  (id = item_id, upsert)

① 질문마다 ── 문서 준비 (RAG 2)
   항목 + 질문 ─► 프롬프트 1 ─► 새 검색어만 ─► 외부 검색 ──────────────► 프롬프트 2 ─► 수집 · 색인
                 검색어 추출    (NF2002 캐시)   조문 목록 / 판례 / 위키       후보 선별      청킹 ─► [law_docs]
                                               + 선택 법령 자체 문서는 항상 ──────────────────┘

② 답변 ── LangGraph
   retrieve ──────────────────────────► generate · 프롬프트 3 ─────► 화면
   메타 청크(항상) + law_docs Top-k      검색된 근거만으로 답 / 팩트체크 / 쉬운 말 풀이    인용 근거만 표시
   (item_id 필터 · similarity|MMR)       근거마다 출처 유형 표시
   병합 · 중복 제거 · 근거 번호
```

### 3-2. 컬렉션과 메타데이터 (명세 2.3)
| 컬렉션 | 내용 | 청크 id | 메타데이터 |
|---|---|---|---|
| `law_meta` | 법률 276건 (20개 분야), 항목당 1청크 | `item_id` (예 `law_001`) | item_id, label, name, abbr, category, ministry, effective_date, url, source_type=`meta` |
| `law_docs` | 조문 · 판례 · 위키 청크 | `item_id:doc_id:순번` (예 `law_001:article-276291-제3조의2:0`, `law_001:prec-621911-holding:0`, `law_001:wiki-12345:4`) | item_id, item_name, doc_id, title, url, **source_type**(`article`·`prec`·`wiki`), query(이 문서를 찾은 검색어), date(시행일/선고일/수정일), chunk_seq, collected_at |

- doc_id 규칙: 조문 `article-{법령일련번호}-{조문}` (법률과 시행령의 같은 "제3조"를 구분), 판례 `prec-{판례일련번호}-{holding|summary}`, 위키 `wiki-{page_id}`

- **item_id 는 검색 범위 필터** — 빠지면 다른 법률의 문서가 근거에 섞인다
- 같은 위키 문서를 두 법률이 수집해도 id 앞에 item_id 가 있어 서로 덮어쓰지 않는다 (F2005)

### 3-3. 문서 수집 (F2003 · F2004)
| 출처 | 검색 | 후보로 보여 줄 것 (프롬프트 2) | 수집할 본문 |
|---|---|---|---|
| 📜 조문 | 선택 법령 + 시행령 본문 1회 수신 → 조문 목록 | `제3조의2(보증금의 회수)` 제목 목록 | 선별된 조문 본문 (항·호·목 포함) |
| ⚖️ 판례 | 검색어별 판례 검색 (사건명) 최대 10건 | 사건번호 · 선고일 · 사건명 | 판시사항 · 판결요지 · 참조조문 |
| 📘 법령해석례 (PDF) | 로컬 `data/casebook.json` 에서 선택 법률과 연결된 사례를 검색어 겹침 순으로 최대 8건 (외부 호출 없음) | 안건번호 · 질의 제목 | 질의요지 · 회답 · 이유 + **파일명 · 쪽** |
| 📖 위키 | 검색어별 위키 검색 최대 5건 | 제목 · snippet | 본문 + URL |

**PDF 변환 (`python -m prep.casebook`, 실행 전 1회)** — 법제처 「2024 법령해석 사례집」(상·하, 1,402쪽) → 사례 312건 JSON.
사례마다 안건번호 · 질의 제목 · 요청기관 · 관련 법령 · 장/절 · 질의요지 · 회답 · 이유 · 법령정비 권고 · 각주 · 쪽 범위를 필드로 나누고, 제목의 「법령명」(시행령 · 시행규칙 포함)으로 항목과 연결 → **108건이 우리 법률 33개와 연결** (건축법 23, 공동주택관리법 14, 주택법 8, 근로기준법 7 …). 쪽 머리글 · 쪽 번호 · 각주는 본문에서 분리 (알려진 한계: 추출 순서가 꼬인 4건은 각주가 본문에 섞임).
→ PDF 를 통째로 글자 수로 자르지 않고 **사례 단위 JSON 으로 먼저 구조화**한 이유: 근거 1개가 "어느 사례의 회답인지" 정확히 가리켜야 하고, 쪽 범위를 출처로 남겨야 하기 때문 (명세 F2004 "파일명과 쪽").

**항상 색인 (선별보다 우선)**: 선택 법령의 제1조(목적)·제2조(정의) 조문, 법령명과 같은 제목의 위키 문서(있으면).
**선별 규칙 보조**: 판례 후보는 대법원 → 최신 선고일 순으로 정렬해 보여 준다. 참조조문은 본문을 받아야 알 수 있어 선별 전 정렬에는 못 쓰고, 판시사항 청크에 함께 넣어 검색·답변 근거로 쓴다 (실측: "임대차보증금" 검색 1위가 상속 사건 → 프롬프트 2가 걸러야 할 대표 사례).
**항목 자체 문서**: 같은 제목의 위키 문서는 법률 105개 중 55개에만 있다 → 법률의 제1조(목적)·제2조(정의) 조문을 108건 모두 "항목 자체 문서"로 항상 색인하고, 위키 문서는 있으면 추가.
**수집 제한 환경 대비** (명세 F2004): API 가 막히면 `data/fallback/` 의 미리 저장한 JSON 묶음을 읽는다.

### 3-4. 청킹 (F2005 · F2016)
`settings.json` 의 `chunk_size` · `chunk_overlap` 으로 `RecursiveCharacterTextSplitter` 를 만든다. 단, **분할 전에 출처별로 문서 단위를 다르게** 잡는다.

| 출처 | 분할 전 문서 단위 | 이유 (설계문서에 기술) |
|---|---|---|
| 조문 | 조 1개 = 문서 1개 → 길면 splitter | 근거 1개 = 조문 1개여야 "제3조의2"로 인용 가능. 조문 대부분이 1,000자 이하라 거의 그대로 유지 |
| 판례 | 판시사항 · 판결요지 각각 문서 | 성격이 다른 두 부분이 한 청크에 섞이지 않게 |
| 법령해석례 (PDF) | "질의요지 + 회답" 1문서 · "이유" 1문서 | 결론(회답)이 긴 이유(평균 3,800자)에 묻히지 않게. 회답은 짧아 거의 1청크, 이유는 splitter 로 분할 |
| 위키 | 문서 전체 → splitter | 서술형 문서라 글자 수 기준 분할이 맞음 |

- 모든 청크 앞에 **헤더** `[주택임대차보호법 제3조(대항력 등)]` / `[대법원 2025다220329]` / `[위키백과: 문서명]` → 본문만으론 어느 법인지 몰라 검색이 흔들린다
### 3-4b. 검색 설정값과 그렇게 정한 이유 (명세 2.5 · 설계문서 필수 항목)
실측 — 법률 8개(주택임대차보호법·근로기준법·전자상거래법·개인정보 보호법·도로교통법·소득세법·의료법·공인중개사법)와 시행령의 조문 1,886개:

| 조문 길이 | 비율 |
|---|---|
| 500자 이하 | 60.8% |
| 1,000자 이하 | **84.9%** |
| 1,500자 이하 | 93.1% |
| 최대 | 15,621자 (소득세법) |

| 설정 | 시작값 | 이유 | 비교 실험 (검증 단계) |
|---|---|---|---|
| `chunk_size` | 1000 | 조문의 85%가 1,000자 이하 → **대부분 조문이 잘리지 않고 근거 1개 = 조문 1개**로 남는다. 500이면 조문 40%가 쪼개져 한 조문이 여러 근거로 흩어진다 | 500 / 1000 / 1500 — 청크 수, 정답 조문 적중, 같은 조문이 근거에 몇 번 겹치는지 |
| `chunk_overlap` | 200 | 긴 조문(항이 많은 것)이 잘릴 때 앞 항의 끝 문장을 다음 청크에 남겨 "제1항에 따른…" 같은 참조가 끊기지 않게 | 100 / 200 / 300 |
| `top_k` | 6 | 근거 = 메타 1건(고정) + 외부 청크 6개. 한 질문의 선별 상한(조문 8 · 판례 3×2부분 · 위키 2)보다 작게 잡아 관련 낮은 청크가 끼지 않게 하면서, 조문·판례·위키가 함께 들어올 여지를 둔다 | 3 / 6 / 10 — 근거 목록 변화, 인용 정확도 |
| `search_type` | similarity | 기본은 유사도. 같은 조문의 이웃 청크나 내용이 겹치는 판례가 몰리면 MMR | similarity vs mmr (`fetch_k` 30, `lambda` 0.5) — F2014 |

- 청크 크기 실험 결과는 설계문서의 "값을 바꿨을 때의 차이"에 그대로 쓴다 (명세 6장)

### 3-5. 검색 · 병합 (F2006 · F2014)
```python
# settings.json
{"chunk_size": 1000, "chunk_overlap": 200,
 "top_k": 6, "search_type": "similarity",     # "mmr" 로 바꾸면 F2014
 "mmr_fetch_k": 30, "mmr_lambda": 0.5,
 "candidate_limit": {"prec": 10, "wiki": 5},
 "select_limit": {"article": 8, "prec": 3, "wiki": 2},
 "chat_model": "gpt-5.4-nano", "embedding_model": "text-embedding-3-small"}
```
1. `law_meta.get(ids=[item_id])` — 메타 청크는 검색 없이 항상 [근거 1]
2. `law_docs` 에서 `filter={"item_id": item_id}` 로 similarity 또는 MMR Top-k
3. **중복 제거**: 같은 청크 id 제거 → 같은 조문의 이웃 청크는 하나로 묶음 → 본문이 거의 같은(앞 200자 동일) 청크 제거
4. 정렬: 메타 → 조문(번호순) → 판례(최신순) → 위키, 1부터 근거 번호

### 3-6. LangGraph (F2007)
```python
class RagState(TypedDict):
    item: dict; question: str; history: list[dict]; mode: str   # "qa" | "factcheck" | "explain"
    sources: list[dict]; answer: str

graph = StateGraph(RagState)
graph.add_node("retrieve", retrieve)   # 3-5
graph.add_node("generate", generate)   # mode 별 프롬프트 3 / 팩트체크 / 쉬운 말 풀이
graph.add_edge(START, "retrieve"); graph.add_edge("retrieve", "generate"); graph.add_edge("generate", END)
```
검증용으로 `graph.get_graph().draw_mermaid()` 출력을 캡처 (명세 4.3).

### 3-7. 프롬프트 세 개 (명세 2.4)
| 프롬프트 | 역할 | 입력 | 출력 형식 |
|---|---|---|---|
| 1 검색어 추출 | 생활법령 전문가 | 법률명 · 목적 · 질문 | JSON 배열 `["임대차보증금 반환", "임차권등기명령"]` 2~4개. 일상어 → 법률 용어 |
| 2 후보 선별 | 법령 자료 사서 | 질문 · 후보(제목+요약만) | JSON `{"article":[번호], "prec":[번호], "wiki":[번호]}`. 쟁점이 다르거나 다른 법이면 버림. 없으면 빈 목록 |
| 3 답변 생성 | 생활법령 안내 도우미 | 근거 목록(번호·유형·제목·본문) · 최근 대화 · 질문 | 결론 → 근거 설명 → 다음 행동. 주장마다 `[근거 N]`. 근거에 없는 조문 번호 금지. 없으면 "제공된 자료에서 확인되지 않습니다" |

선별을 따로 둔 이유: 본문을 받기 전에 버릴 문서를 정해 **외부 호출 수를 줄인다** (판례 10건 중 3건만 본문 요청).

- 하이브리드(v12): 점수 변화 없음. 조문 지목을 끄고 검색만 비교하면 정답 조문 28 → 27/32 (월세 인상 조문을 키워드 순위가 밀어냄), 가중치 0.3 · 0.5 도 27/32 → **끔**.
- 재순위화(v13 · v15): W01 은 찾지만 W10 인용을 놓쳐 인용 적중은 v11 과 같고, LLM 호출이 하나 늘어 응답이 2배 가까이 → **끔**.
- 법령용어 → 조문 연결(v14, 국가법령정보센터 `lstrmAI` · `lstrmRltJo`): "대항력 → 주택임대차보호법 제3조", "해약금 → 민법 제565조" 처럼 연결은 정확하지만 용어 이름이 정확히 같아야 해 이번 실패(W01)에는 걸리지 않았고, 처음 질문마다 API 호출이 많아 느림 → **끔**. 세 기능 모두 코드와 설정은 남겨 둠.
- v2 → v6 에서 검색 적중률이 내려간 것은 프롬프트 1 형식이 바뀌어 검색어를 새로 만들었기 때문 — **검색 결과가 프롬프트 1 의 검색어에 크게 좌우된다**는 것이 확인됐다.

### 쟁점 나누기 모드 — 여러 법이 얽힌 복합 질문 (`service/complex.py`)
"미성년자 A가 명의를 도용해 이중계약 … 천재지변으로 붕괴 … 제3자 D 피해" 같은 질문은 쟁점이 5~6개, 법률도 여러 개다.
고른 법률 하나 · 근거 8개 구조로는 덮이지 않는다 → 첫 화면 검색창에 긴 상황(40자 이상)이 들어오면 먼저 쟁점을 나눈다.

1. 쟁점 분해 (LLM 1회) — 276개 법률 이름 목록을 주고 쟁점마다 법률 1~2개 · 검색어, 결론이 갈리는 사실은 '가정'. 쟁점이 2개 미만이면 지금처럼 법률 카드
2. 쟁점별 근거 — 그 법률의 조문을 색인(처음 한 번), 조문 목록에서 정답 조문 지목(검색 개선 1) + 검색. 쟁점끼리 동시에 처리
3. 근거 담기 — 지목한 조문을 먼저 모두, 남는 자리(최대 22개)를 검색 결과로 쟁점끼리 번갈아
4. 쟁점별 답변 (LLM 1회) — 쟁점 → 적용 규정 → 상황 적용(가정은 "만약 ~라면"으로 나눠) → 정리 → 한눈에 보기, 끝에 전문가 상담 안내 문장 고정

평가 (`data/eval_complex.json` 4문항 · 정답 조문 18개, `python -m scripts.eval_complex`)
| 방식 | 쟁점 적중률(검색) | 쟁점 적중률(인용) | 시간 |
|---|---|---|---|
| 법률 하나로 묻기 (가장 관련 깊은 법률을 사람이 고름) | 44.4% | 38.9% | 21~32초 |
| 쟁점 나누기 — 처음 | 61.1% | 55.6% | 26~41초 |
| + 지목 조문을 먼저 담기 | 66.7% | 66.7% | 22~46초 |
| + 분해 프롬프트에 민법(물권) · 주택임대차 · 자배법 안내 | **83.3%** | **66.7%** | 30~36초 |

- 처음엔 법률 2개짜리 쟁점에서 둘째 법률의 지목 조문이 근거 상한에 밀려 잘렸다 → 지목 조문을 먼저 담아 해결
- 분해 프롬프트에 법률 이름만 주면 "도난품"을 민법(물권)으로 보내지 못했다 → 민법 부분별로 다루는 일을 적어 줌 (선의취득 0/3 → 3/3)
- 쟁점 분해가 실행마다 조금씩 달라 적중률이 66~83% 사이에서 흔들린다. 남은 실패는 공작물 책임(제758조) · 최우선변제(제8조) 등

### 평가로 정한 최종 검색 설정 (`settings.json`)
| 설정 | 값 | 정한 근거 |
|---|---|---|
| `chunk_size` / `chunk_overlap` | 1000 / 200 | 500/100 · 1500/300 보다 적중률이 높음 (`docs/compare_chunks.md`) |
| `embedding_model` | text-embedding-3-large | small 85.7% → large 90.5%, 일상어 ↔ 조문 의미 거리 문제 해결 |

| `expand_articles` | true | 조문 청크가 잡히면 조문 전체를 근거로 (긴 조문의 다른 항 문제) |

| `temperature` | 0 | 실행마다 인용 · 거절 결과가 흔들리던 것을 줄임 |
| `pin_articles` | true | 조문 목록에서 정답 조문 지목 → 25문항 90.5 → 100%, 넓힌 분야 인용 81.8 → 90.9% (LLM 호출 수 그대로) |
| `hybrid` / `rerank` / `term_links` | false | 각각 정확도 이득이 없거나(하이브리드 · 용어 연결) 인용 적중은 같은데 2배 느림(재순위화) — 위 비교 참고 |
